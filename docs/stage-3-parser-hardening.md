# Этап 3: устойчивый MAX-парсер и прокси

## Архитектура

Каждый MAX-аккаунт имеет собственный `storage_state`, постоянный прокси и состояние здоровья в PostgreSQL. Один цикл парсера защищён распределённой арендой `ParserLease`, поэтому две реплики Coolify не запускают один и тот же сбор одновременно.

Прокси не передаётся аргументом процесса, не возвращается в открытом виде в API и хранится в `MaksAccount.proxyString` как AES-256-GCM envelope. Старые незашифрованные значения автоматически шифруются при обнаружении файла сессии.

## Переменные окружения

- `PARSER_PROXY_ENCRYPTION_KEY` — постоянный случайный секрет не короче 32 символов. Если не задан, временно используется `AUTH_SESSION_SECRET`.
- `PARSER_SESSIONS_DIR` — каталог файлов сессий. Для нового контейнера рекомендуется `/app/data/sessions` с persistent volume.
- `PARSER_WORKER_TIMEOUT_MS` — таймаут одного чата, допустимо 30000–300000; по умолчанию 120000.
- `PARSER_DEBUG_ARTIFACTS=false` — снимки страниц выключены, поскольку могут содержать персональные данные.
- `PARSER_AUTH_HEADLESS=false` — QR-авторизация требует графической среды или подключённого desktop/VNC.

Нельзя менять `PARSER_PROXY_ENCRYPTION_KEY` после создания аккаунтов без отдельной ротации ключа: существующие прокси перестанут расшифровываться.

## Python и Chromium

Зависимости зафиксированы в `requirements.txt`. В образе Coolify должны выполняться:

```bash
python -m pip install --no-cache-dir -r requirements.txt
python -m playwright install --with-deps chromium
```

Версия Python-пакета Playwright должна совпадать с установленными браузерными бинарниками.

## Persistent volume

Файлы `storage_state` эквивалентны активной авторизации и не должны попадать в Git, резервные копии без шифрования или публичные volumes.

Для нового развёртывания:

```text
PARSER_SESSIONS_DIR=/app/data/sessions
Coolify volume: /app/data/sessions
```

Если текущие рабочие сессии уже находятся в другом volume, сначала скопируйте их в новый каталог и проверьте владельца/права. Не переключайте переменную на пустой каталог до копирования.

## Выкладка

1. Создать резервную копию PostgreSQL и каталога сессий.
2. Установить неизменяемый `PARSER_PROXY_ENCRYPTION_KEY`.
3. Применить миграцию:

```bash
npm run db:deploy
```

4. Собрать новый образ с Python Playwright и Chromium.
5. Подключить persistent volume сессий.
6. Перезапустить одну реплику и проверить `/api/admin/auth/sessions` через админку.
7. Только после smoke-test масштабировать приложение до нескольких реплик.

## Поведение защиты

- `ACTIVE` — аккаунт готов.
- `COOLDOWN` — временная ошибка или ограничение; применяется экспоненциальная пауза до 6 часов.
- `PROXY_ERROR` — прокси недоступен; первичная пауза 15 минут.
- `AUTH_REQUIRED` — сессия истекла, аккаунт выключается до нового QR-входа.
- `DISABLED` — аккаунт вручную поставлен на паузу.

Worker использует штатный Chromium без подмены `navigator.webdriver` и искусственного User-Agent. Для снижения нагрузки применяются последовательная ротация аккаунтов, небольшие паузы, плавный скроллинг и прекращение запросов при `429`, проблемах прокси или истёкшей авторизации.

## Smoke-test

1. Открыть список аккаунтов: пароль прокси нигде не должен отображаться.
2. Добавить тестовый аккаунт через резидентский прокси и пройти QR-вход.
3. Убедиться, что строка `MaksAccount.proxyString` начинается с `enc:v1:`.
4. Запустить один тестовый чат вручную и проверить `status=ACTIVE`, `lastSuccessAt`, `totalRuns`.
5. Запустить синхронизацию одновременно из двух запросов: второй должен вернуть сообщение, что парсер уже выполняется.
6. Остановить прокси: аккаунт должен перейти в `PROXY_ERROR`, пароль не должен появиться в логах.
7. Вернуть worker ответ `429`: аккаунт должен перейти в `COOLDOWN` минимум на час.
8. Завершить MAX-сессию: аккаунт должен перейти в `AUTH_REQUIRED` и перестать использоваться.
9. Перезапустить контейнер и убедиться, что файлы сессий сохранились в volume.

## Откат

Миграция только добавляет столбцы и таблицу. Предыдущий код можно временно вернуть без удаления новых данных. Не удаляйте `ParserLease` и новые поля `MaksAccount` при наличии активных процессов; сначала остановите cron и дождитесь завершения worker.
